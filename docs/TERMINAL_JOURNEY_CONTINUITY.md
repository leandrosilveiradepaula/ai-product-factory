# Continuidade operacional V2 após entrega terminal
Candidato não aplicado. A política main_snapshot com pins explícitos não deve ser desativada quando main avança. A rotação só ocorre para pedido real autenticado, ainda sem tarefa, após conclusão da jornada anterior e autorização explícita por projeto. O broker verifica que tanto a origem anterior quanto o SHA efetivamente entregue são ancestrais de main. Se a entrega anterior existe somente em Preview, retorna journey_prior_preview_not_released antes de criar qualquer ref. Não confundir fechamento de Preview com release. O CRM #209, PR #213 e a main consultada em 24/11/2026 estão precisamente nessa situação; preservar a entrega, não recuar para legado nem publicar por atalho.

A nova migration instala RPCs service_role-only, duas tabelas RLS sem política pública e nenhum dado ou autorização inicial. Depois de merge humano, QA e autorização de instalação, um admin ativo pode autorizar factory_authorize_journey_refresh_v2 com CAS de versão/geração/digest. A autorização permite ao worker criar uma única branch preview/journey-base-<UUID da jornada> no SHA real de main, somente para demanda legítima; em repositórios cuja integração Vercel constrói refs preview/** isso pode consumir quota de Preview. Autorizar somente dentro da política e quota existentes; nenhuma compra ou novo serviço. Não executar a autorização por integração genérica fingindo identidade humana.

O runtime usa preflight SQL, verificação GitHub de ancestralidade, rechecagem de epoch/refs, ensure_branch_at_sha idempotente e transação CAS com recibo. Nunca força branch, muda a jornada terminal, cria modelo, faz merge ou autoriza release. Se main mudar no intervalo, falha fechado, preserva o recibo e não sobrescreve o Preview. O novo intake continua pelo binder V2 existente após reler política/controle. Rollback: revogar opt-in via mesma RPC, preservando recibos e históricos. Não excluir política nem reutilizar lineage antiga.

O gate de entrega continua humano. Não aplicar a migration nem configurar autorização automaticamente no deploy. Não autorizar Start sintético. A PR #213 do CRM é uma entrega separada ainda sujeita a gate de release e evidência atual.
